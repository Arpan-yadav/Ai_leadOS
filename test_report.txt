AI LeadOS - Comprehensive Test Case & Deployment Report
1. Executive Summary & Testing Journey
The testing journey for AI LeadOS has been a rigorous, multi-stage process designed to ensure absolute reliability, data security, and strict tenant isolation across the platform. Our approach mandated that developers could not test their own code, enforcing a strict cross-team verification model among the AI/Automation, Frontend, and Backend teams.
Throughout the journey, we faced and resolved complex challenges, particularly around Dependency Injection in our testing modules (e.g., mocking the PrismaService, TasksService, and AiService across intertwined modules). We established a comprehensive suite of Unit Tests using Jest for the backend and React Testing Library for the frontend. We heavily utilized mocking to isolate services, ensuring that our business logic—especially the complex AI Email Routing, WhatsApp Meta Webhooks, and Multi-SMTP fallback systems—was tested exhaustively without affecting production databases.
2. Environment & Deployment Details
Frontend Environment (Vercel)
The Next.js 14 frontend application is deployed on Vercel. Vercel was chosen for its seamless CI/CD integration with GitHub, Edge Network caching, and optimized rendering strategies (Server-Side Rendering and Static Site Generation). Environment variables are securely injected at build time, protecting sensitive OAuth keys and API secrets. Every push to the main branch triggers an automatic immutable deployment, followed by automated smoke tests to ensure UI stability.
Backend Environment (Render)
The NestJS backend infrastructure is hosted on Render. Render provides a robust, Docker-containerized environment that scales horizontally. The backend service is configured to auto-deploy upon passing GitHub Actions checks. Render’s private networking is utilized to securely connect the Node.js application instances to internal Redis caches (for rate limiting and job queues) and our PostgreSQL database.
Database & Data Layer (Supabase PostgreSQL)
Data persistence is handled by a managed PostgreSQL instance on Supabase. To handle high concurrency, connection pooling via PgBouncer is enabled. Strict Row-Level Security (RLS) is mirrored in our application layer via Prisma middleware to enforce tenant isolation—guaranteeing that Tenant A can never query or manipulate Tenant B's leads, deals, or communication logs.
